# LoRA Comfy Combiner: restart assessment

Evidence date: 3 October 2026. This is a discovery checkpoint and proposed delivery plan, not a release or proof of improved image quality.

## Recommendation

Keep the useful code and reset the product contract, roadmap and acceptance criteria. Complete one FLUX.1 workflow before expanding the engine across architectures. The owner selected FLUX.1 first during this review.

The app should help one person on Bender select compatible LoRAs, describe their intended contributions, obtain explainable **individual block weights**, and copy each LoRA's complete block vector into a compatible ComfyUI loader. The block vector is the primary product output; a single overall strength is only a supporting setting. The initial FLUX target is Inspire Pack **LoRA Loader (Block Weight)**; additional families may use another verified loader or a focused companion node. It does not merge LoRA files. It cannot guarantee good images from weights alone.

### What better maths means

For ordinary LoRA, the effective update is derived from the paired low-rank factors, with the loader's rank/alpha scaling. Summing the norms of the individual factors is not equivalent to measuring that update: rescaling one factor and inversely rescaling the other leaves the update unchanged while changing those separate norms. Start with architecture-aware pairing and effective-update statistics, preserving sign, scale and the distinction between measured distribution and a recommended multiplier.

Even better update statistics cannot identify 'this block is clothing' universally or predict every visual interaction. The desired behaviour is to help stacked LoRAs coexist by adjusting their individual block contributions, including overlapping or nearby groups. Structural overlap is a useful comparison view, not proof of visual interference, and neighbouring blocks do not establish shared semantics. Role budgets, collision scores and presets remain policies until tested against controlled ComfyUI outputs. Use fixed base model, prompts, seeds, sampler/scheduler, steps and LoRA versions; compare each LoRA alone, naive stacking, the existing policy and the proposed result. Assess identity, clothing/pose adherence, unwanted bleed and artifacts across several cases. Keep manual variants as first-class evidence, not overrides that disappear on recomputation.

A sensible implementation progression is: truthful export and explicit manual controls; explainable conservative recommendations; then calibrated family-specific presets and an optional later local comparison/search assistant. An LLM or cloud service is not required for the application.

## Proposed release plan

1. **R0 — Restart baseline.** Preserve source/database/profiles; refresh local read-only catalogue audit; add current intent contract, scope, support matrix and checks. Separate historical Nibbler records from Bender state. Snapshot user data before any migration.
2. **R1 — Trustworthy FLUX export.** Pin installed loader behaviour; fix BASE/order/sparse/CLIP/global semantics; unify native entry point and backend/frontend result ownership. Add export contract and regression tests.
3. **R2 — Defaults, variants and recipes.** Immutable Default versions; named personal variants with parent/default version and change history; explicit profile selection in composition; saved recipes capture exact inputs, settings, engine version and resulting output. Reset selects Default without deleting personal history.
4. **R3 — GUI and complete daily workflow.** Owner chooses a visual direction through the local questionnaire; implement library selection, role/priority review, visible per-block comparison and editing, balance explanation, full-vector copy per node, save/reload/reset. Integrate keyboard access and clear unsupported states. Explanations and advanced maths can be disclosed progressively; block weights must remain central rather than hidden behind an overall strength control.
5. **R4 — FLUX acceptance.** Controlled local ComfyUI comparisons and owner visual review. Release only when the chosen workflow is reproducible and useful. Label remaining recommendation uncertainty plainly.
6. **R5 — Family expansion.** Add the requested families one at a time using the same adapter/export/visual gates. LTX-2.3, LTX-2.5 and MiniMax H3 are explicitly included. Analysis/comparison foundations can proceed before loader support; research compatible existing nodes and build a focused companion node if necessary. FLUX remains the first complete workflow.
7. **R6 — Finish.** One-click Bender loopback launcher, local asset bundle, operation guide, reproducible environment, tested backup/restore, release tag and known limitations. A companion node, if needed, remains narrowly tied to required export support; no LAN service or unrelated product expansion.

R0/R1 and GUI discovery can progress independently. Do not continue the old chain of forensic sub-phases as the product roadmap. Define completion around the user's complete workflow.

### Local runtime and maintenance

Recommended target: build the existing React UI and serve it with the local API, behind one Bender launcher and one loopback origin. This is a proposed simplification, not implemented. Keep network binding explicit (`127.0.0.1`, and `::1` only if deliberately supported), local resources bundled, and no background runtime downloads or telemetry. A desktop wrapper is optional later, not needed to get a professional local interface.

Keep dependency updates targeted and locked. Split the large UI/API files along actual responsibilities while delivering features; do not schedule a broad refactor before fixing behaviour. Use header-first inspection and cached, cancellable analysis keyed by file identity and analysis version. Do not load every library tensor just to browse/search.

### Checks and acceptance

Use focused Python tests, synthetic architecture/key fixtures, paired-factor/scaling invariance cases, exact loader-export tests, profile/recipe round trips, UI tests/build/lint and a read-only representative-file Characterisation pack. Test against a copied database for migrations and restore. Add CI that does not depend on private LoRA binaries or access to Bender. Independent review precedes push/merge; current source inspection or unit tests are never described as image-quality acceptance.

This project has no existing hosted Characterisation workflow to invoke. Establish one appropriate to its requirements rather than assuming another repository's workflow exists here. Record test results and limitations in the restart receipt.

## Backup and recovery

The owner's reported AOMEI scripts backup to Leela is useful but does not establish coverage of this project's E: paths. No backup schedule was inspected or changed.

Back up source/history and locked environment manifests; a consistent SQLite snapshot including personal/combined profiles; external profile JSONs; app configuration and calibration recipes/results. Decide which LoRA binaries are irreplaceable and back those up, retaining hashes/source information for the remainder. Git excludes the database and is not a substitute for user-data backup. Do not assume reindexing reconstructs personal profiles.

Use SQLite's backup facility or a cleanly stopped app; copying a live database file alone can omit WAL state. Keep versioned backups, a second-device copy on Leela and an off-site copy with an actual restore test into a separate directory. Verify restored settings, profiles, recipes and model-path mapping before declaring recovery complete. Google Drive sync alone is not retention/versioned recovery proof.
